> 2026-09-25 **v1.2 QTE 提速**: 只减"每轮要看多少像素", **不动闭环语义** ——
> **两级截屏区**: 未锁定箭行时扫主屏中央横带 (本机 3891x792 ≈ 3.08 MP); 识别到箭行后改用
> `qte_track_region()` 推出的**紧凑小窗** (~1117x333 ≈ 0.37 MP, 像素少 8.3 倍) 轮询,
> 每 `qte_sweep_ms` (250 ms) 仍全横带扫一次兜底; **刚按过键却抓空 → 立刻全扫复核**;
> `_qte_region()` 变了 (换分辨率/换主屏) 则小窗作废重学; 学小窗只用**选中行**的 bbox
> (防桌面干扰物把窗撑大)。另有三处常数级优化: **线程本地复用 mss 实例** (省 ~7 ms/帧)、
> **`grab(region, gray=True)` 灰度直出** (少一份 3 MP 中间图, 异常时自动重建实例)、
> **掩膜改 `cv2.inRange`** (3 MP 上 4.4 ms → 0.8 ms; 连通域只关心"非零", 两种写法结果等价,
> 已用全部历史样张逐项比对确认零回归)。默认值: `qte_hold_ms 45→30`、`qte_poll_ms 120→80`,
> 新增 `qte_fast_ms=5` (按键后快速重轮询) / `qte_sweep_ms=250` (兜底全扫周期)。
> 实测 (端到端仿真已校准到 v1.1 的 302 ms/键): **本工具每键开销 ≈165 ms → ≈45 ms,
> 4 键总耗时 1.59 s → 1.15~1.18 s (提速 21~29%), 首键 245 ms → 145 ms**, 零误按零重复。
> **状态机 `_qte_maybe_send` 一个字没改** —— 提速全部来自"每次轮询看更少的像素",
> 不来自提前连发 (提前连发正是"输入错误率太高 / 行尾卡死"的成因, 不得回退)。
> 速度地板 = 游戏自身消耗延迟 (~200 ms, 不可控) + 小窗一轮 ~16 ms (其中 13.9 ms 是
> 144 Hz vsync 抓图硬地板), 详见"QTE 延迟预算"。
> 2026-09-25 **v1.3 QTE 延迟收尾**: 把抓图成本模型重新实测 (GDI/mss 抓图 <=0.8 MP 是
> **6.9 ms 硬地板** = 144 Hz 一帧, 与区域大小无关; 之后才按像素涨: 1.68 MP=13.9 /
> 3.08 MP=27.7 / 6.73 MP=45 ms), 据此做四处收尾, **状态机语义依旧零改动**:
> 空闲轮询 `qte_poll_ms` 80→50 (**首键 137→107 ms, -30 ms**)、快速窗 `qte_fast_ms` 5→2、
> 新增 `qte_sweep_relax_ms`=900 (已锁小窗且本行已按过键、画面正常推进时, 兜底全横带扫描
> 从 250 ms 放宽到 900 ms, 去掉跟踪期每 250 ms 一次 ~42 ms 的离群帧; 行消失/抓空/未按键
> 自动回 250)、启动时 `timeBeginPeriod(1)` 把全进程定时器提到 1 ms 格 (atexit 还原;
> 本机浏览器已提权故无差, “干净”机器上 sleep/hold 不再被 15.6 ms 量化, 省 ~10 ms 级)。
> 4 键总耗时再 -2~7%; 220 ms 档键间隔 238 ms = 游戏消耗 220 + 工具 ~18, **已贴物理地板**。
> **评估过两条 GPU 取帧路径, 实测后都不上** (详见“QTE 延迟预算 → v1.3”):
> ① **dxcam (DXGI DDA)** —— 本机开着 HDR, DDA 表面是 `rgba16f` (FP16) 而非 BGRA8,
> 按 BGRA8 解读就是之前看到的“花屏”(整屏 79% 像素不符、单帧内部自相矛盾)。
> **真因是格式错配, 不是驱动 bug** (修正 v1.3 早前的判断)。但即便按 FP16 正确解码,
> `acquire_frame` 30 帧耗 715 ms (~24 ms/帧) 并不比 GDI 快, 且 `cv2.cvtColor` 不吃
> float16, 还得自己转 → 收益为零, 弃用。
> ② **windows-capture (WGC)** —— 内容与 mss 逐像素一致 (max diff = 0), 识别结果完全相同,
> 但**变更检测不快于 GDI**: 同进程双路径并行测同一次画面翻转, mss 中位 17.3 ms vs
> WGC 中位 20.3 ms (配对差 mean −5.4 / median −9.1 ms, 负值 = WGC 更慢)。
> WGC 受 DWM 合成与帧投递管线时延约束, 弃用。

> 2026-09-25 **v1.4 CPU 开销控制** (识别逻辑与闭环语义一字未改, 只砍"每次看多少像素 /
> 用多少线程 / 一秒看几次"):
> ① **OpenCV 线程 12 → 4** (`cv2_threads`): 默认值 = 逻辑核数时, 一次全横带识别烧 66 ms CPU
> 只换来 18.7 ms 墙钟; 限到 4 线程后 **全横带 66→44 ms、窄条带 33→14 ms, 墙钟几乎不变**
> (窄条带 20.4→21.0 ms)。更关键的是不再每秒 20 次唤醒全部核心去和游戏的 worker 线程抢核。
> ② **持久窄条带** (`qte_zone`, 写进 config.json 跨会话复用): QTE 箭行是固定 UI 位置,
> 学到一次就一直有效; 存的是"相对全横带高度的比例", 换分辨率/换缩放自动换算不会失配,
> 数据不可信 (太窄/几乎等于全带/损坏) 时自动退回全横带。实测全横带 2.17 MP → 窄条带 0.61 MP:
> **CPU 44.4 → 13.8 ms (-69%), 墙钟 45.8 → 21.0 ms (还快 25 ms)** —— 这次省 CPU 与降延迟同向。
> ③ **空闲轮询 CPU 调速器** (`qte_cpu_budget`, 默认 25% 单核): 用实测 EMA 每轮开销反推最小
> sleep 保证占空比不超预算, 换更高分辨率/更花画面时自动降频, 不会把一个核心吃满;
> **只约束空闲态**, 按键后的快速窗与正在跟踪箭行时不受限 (延迟关键期)。
> ④ 未锁条带时的兜底全扫周期 `qte_idle_sweep_ms`=1000。
> exe 级实测 (i7-8700K, 计入 onefile 父子进程): **B 未学条带 44.7% → E 已学窄条带 33.1% 单核**;
> QTE 延迟与 v1.3 持平 (端到端仿真 4 键总耗时 1.04~1.21 s / 每键 93~104 ms / 首键 ~96 ms,
> 14~26 ms 各档全部无回退), 样张方向序列与窄条带一致性回归全绿。

> 2026-09-25 **v1.5 挂机 CPU 归零** (逐线程归因后定位到真正的头号开销: 悬停轮询空读):
> v1.4 之后仍有 ~19% 单核降不下去, 而且"QTE 全关、只开实时跟踪"时也一样 ——
> 逐线程归因 (`work\probe_cpu_threads3.py`) 指后台悬停轮询, 再单轮拆解
> (`work\probe_hover_cost.py` / `probe_hover_prof.py`): **一轮"鼠标旁没有坐标标签"的空读
> = 86 ms CPU** (本进程 61 ms + 常驻 PowerShell OCR worker 25 ms; 内容是 2.7 次 mss 截屏
> ≈12 ms/次 + 2.7 次 WinRT OCR 的三级放大框级联)。按 0.6 s 周期就是 **14.3% 单核**
> (1.5 s 周期 5.7%), 而且**不管前台是不是游戏都在烧** —— 切出去看攻略、排队挂机全是白烧。
> 加两道**只影响后台轮询、不影响 F1/F2 实时读取**的空闲闸:
> ① **前台闸** `hover_gate`: 前台窗口不属于游戏进程 → 0.5 s 轻量复查, **完全不截屏不 OCR**。
> 判定抽成 `_game_foreground()`, 与 QTE 闸门共用; (hwnd,pid)→进程名缓存命中 ~10 µs
> (未命中 ~88 µs), pid 一起进 key 防 hwnd 回收复用认错进程; **任何异常都当"是游戏"(True)**
> —— 闸门只用来省 CPU, 绝不能挡住功能。状态翻转时只在日志提示一次, 不刷屏。
> ② **静帧闸** `hover_static_skip`: 光标静止 ≥2.5 s 且"鼠标近旁并集区域"与上一轮**逐位相同**
> → 读数不可能变, 整轮跳过 OCR 并把缓存时间戳顺延 (F1/F2 的 2 s 兜底照旧有效)。
> 指纹区域 = `hover_box ∪ 自动搜索框 ∪ 回退框` (本机 680x660), 一次 **13.8 ms** vs 空读 86 ms
> → 静止挂机 5.7% → **0.9% 单核**; 且**只在光标静止时才算指纹**, 光标一动就是零额外开销。
> 读取抛异常时作废静帧基线, 下一轮必须重试 (不会因一次失败永久跳过)。
> ③ 关掉实时跟踪 (`live_target=false`) 时轮询一律走慢周期 —— 那时没人消费读数, 只喂 2 s 缓存。
> **QTE 状态机、按键时序、延迟预算一个字没改** (样张方向序列 / 窄条带一致性 /
> 端到端 4 键延迟 / 历史截图误检对照, 全部回归通过)。真游戏同屏实测见 "CPU 开销实测" 一节:
> **老 v1.1 副本 70.9% → v1.5 默认 11.2% 单核 (-84%)**; 同为跟踪态, 关掉两道闸 (= v1.4 行为)
> 是 18.6%, 即闸门本身又省了 40%。

> 2026-09-26 **v1.6 QTE 错误率收口** (识别只做加法, 闭环按键时序模型不动):
> 用户反馈"输入太快 → 错误率高 → 一错就整行重来"。逐帧复盘 `artillery.log` 后定位到**两条
> 互相独立的成因**, 其中头号成因与识别精度无关:
> ① **同一台机器上跑了两个实例** —— `Downloads\WARDOGS_Artillery (2).exe` 这份旧副本从
> 17:51 起一直开着 (累计 6994 CPU 秒), 与新实例**同时往游戏里发方向键**。日志显示它在
> 23:25–23:49 仍在发 `QTE -> 上/右 (1/2)`。游戏侧收到交叉的按键流 → QTE 整行判错重来,
> 表现就是"错误率突然很高"。**任何时候只允许运行一个实例** (见"已知限制")。
> ② **红填充箭行灰度通道全瞎** —— 日志 17:49:03 出现"1 秒内连发 5 键"的签名: 红箭的填充色
> 与它自己的暗描边**灰度值几乎相同**, 灰度掩膜里整行箭被描边吃掉, 工具时而抓空时而只抓到半行,
> 状态机把"抓空"当成"游戏已消耗那一支"继续推进 → 串键。修法: 新增**红箭彩色通道**
> (`find_qte_arrows(color_img=...)`, 判定 `R>=140 且 G,B<=95`, 常量 `QTE_RED_MIN`/`QTE_RED_GB`),
> **只在灰度通道抓空时才跑**, 且先过 **stride-4 存在性闸** `_red_present()`
> (0.27 ms/0.73 MP) —— 画面里没有饱和红就一次连通域都不做。红掩膜改用**单趟 `cv2.inRange`**
> (替代三张 bool 中间图), 6.8 → 0.78 ms (**8x**)。红通道与灰度通道**共享同一套 >=10 px 小箭
> 下限**: 早先的半分辨率探针会把下限抬到 20 px, 实测 0.60x/0.53x 缩放整行红箭直接抓空,
> 故改为"存在性闸 + 全分辨率连通域" (缩放回归由 FAIL 转 PASS)。
> 另加**三道错误率闸**, 全部只"延迟按键", 绝不提前连发:
> * **行稳定防抖** `qte_row_stable_ms=70`: 候选新行必须连续读到 70 ms 且序列不变才认,
>   过滤弹出动画的中间帧/半行帧 (回归项 `transient row no press` / `flipping seq no press`)。
> * **置信度门** `qte_press_margin=0.10`: 选中行的最小模板 IoU margin 低于 0.10 就不按
>   (回归项 `low margin no press`)。安全裕量实测: 36 个真行 min_margin = 0.195 (**2x 裕量**),
>   红样张 1.0x→0.4x 缩放 margin 0.148~0.249。
> * **最小键间隔** `qte_min_gap_ms=100` + **按键时长** `qte_hold_ms` 30→**40**: 两次 keydown
>   至少隔 100 ms (挡住"同一帧被重复消费"造成的连发); 40 ms 的 hold 给游戏留足采样余量
>   —— 漏键的代价是整行重来, 而 40 ms 仍远小于 100 ms 间隔, 所以**对速度零影响**。
> 红箭行活跃期轮询加下限 `qte_red_poll_ms=8` (消耗反馈只有颜色通道看得见, 8 ms 既跟手又把这段
> 占空比压在 ~13% 单核); 空闲期红探针限流 `qte_red_probe_ms=250` (4 Hz)。
> 配套改动: `_qte_scan` 由 `grab(region, gray=True)` 改为**恒截彩色**再 `cvtColor` 转灰度
> (颜色通道是红箭的唯一入口), 代价 ~+3 ms CPU/全横带帧 (实测 `cvtColor BGR2GRAY` 3.05 ms)。
> 回归: `test_qte_red.py` **14/14 PASS** (含红行全分辨率/半分辨率一致性/0.60x/0.53x 缩放/
> 白箭不回退/2 个负样本/4 个状态机门), `test_qte_band.py` / `test_qte2.py` / `test_qte_speed14.py`

## 使用方法

1. 游戏设置改为 **无边框/窗口化** (独占全屏抓不到图)。
2. 打开游戏全屏战术地图: 鼠标移到某点时, 鼠标旁会出现白色悬停坐标标签 `xNN.NN / yNN.NN`。
3. **实时跟踪 (F8, 默认开)**: 全屏地图里鼠标悬停到哪儿, 目标坐标就持续更新到哪儿
   (后台 0.6 s 轮询直接提交), HUD 距离/方位/仰角随之实时刷新, 无需反复按 F1。
   **F1 = 手动读目标**, **F2 = 读炮位** (与 F1 完全相同的取点方式)。
4. 两者齐备后自动解算: 距离 / 方位 / 仰角 mil / 弹道 / 装填 / 射程窗口判定。
5. HUD (F5 开关): 置顶半透明小窗, 实时显示 距离 / 方位 / 仰角 / 目标坐标 / 炮位坐标;
   按住 **F7** 拖动位置, 双击关闭; 无边框游戏之上常驻可见 (周期性强置顶 + 鼠标穿透)。
   窗口大小按内容与系统缩放自适应 (125%/150% 高缩放屏不再切掉底行)。
6. 主界面按钮 (2026-09-22 精简后共 6 个, 与热键等价, 游戏中无需切窗):
   **读取目标 (F1)** / **读取炮位 (F2)** / **HUD 开关 (F5)** / **实时跟踪 (F8)** /
   **QTE 自动 (F9)** / **保存设置**。
   - 三个开关按钮 **HUD / 实时跟踪 / QTE 自动** 开启时绿色高亮显示 `● 开`,
     关闭时灰色显示 `○ 关`, 状态一眼可见。
   - 底部 **运行日志** 默认收起, 只保留一行最近事件; 点按钮可展开/收起,
     配置键为 `ui_log_open` (默认 `false`)。
   另有纯热键: **F7** 按住拖动 HUD, **F10** QTE 立即读一次 (按钮已移除, 热键保留)。
7. **QTE 自动输入 (F9/F10)**: 出现一横排方向箭提示时, 按从左到右顺序自动按下对应方向键
   (下/左/右/上)。F9 = 后台 ~8Hz 持续识别自动按; F10 = 只识别并按一次 (不等防抖)。
   F9 是"边检测边按"的**视觉闭环** (每轮询至多按一键), 默认 `qte_model=consume`:
   - **消耗型** (WARDOGS 实测: 按对的箭变绿后检测器就看不到它, 所以"检测到的行"
     就是还没按的尾段): 以**画面为准**推进 —— 画面 == 记录行尾段就按下一支,
      无防抖; v1.3 后**本工具每键开销 ≈18 ms** (按键后轮询加速到 `qte_fast_ms`=2 ms,
      空闲轮询 `qte_poll_ms`=50 ms);
   - **画面不变就不连发**: 上一帧已经按过且画面没变时保持沉默, 等游戏把箭吃掉。
     提前连发会让状态机与游戏失步 → 整行重按 → **行尾永久卡死**
     (这就是"最后一个按不出来"的机制);
   - **丢键兜底**: 画面持续不变超过 `qte_retry_ms` (默认 900 ms) 就补发最左那支一次,
     兜住按键被 UIPI/切窗吞掉的情况 (900 ms 远大于实测显示滞后 ~230 ms, 不会误触发);
   - **静止型** (`qte_model=static`, 箭不消失/逐个弹动的游戏): 当前行以已按序列为前缀
     且更长时, 按右边新出现的那支; 此时"画面不变即沉默"与丢键兜底自动失效;
   - **同一支箭绝不重按**: 漏帧时以画面重新对齐, 不重按整行; 我们多按了就沉默等画面追上;
     整行按完后沉默直到箭行消失 (连续 4 帧空);
   - **淡出残行抑制**: 记录行已按区的连续切片残行直接忽略;
   - **行中孤箭噪声**: 只剩 1 支且不是期望尾段时忽略但不清状态; 空状态时孤箭不开新行;
   - **新行防抖**: 与记录行对不上的新行, 首键等 2 帧 (~0.24 s) 稳定再按;
   - **前台闸**: 仅当前台窗口是游戏进程 (`qte_game_exe`, 默认
     WardogsClient-Win64-Shipping.exe) 时才跑识别, 桌面/浏览器里的亮色图标不会
     误按方向键; `qte_gate=false` 可关闸 (样张联调用)。
    间隔/按住时长/轮询周期/快速轮询/兜底全扫周期/补发阈值与上限/看门狗/行模型见
    `config.qte_gap_ms / qte_hold_ms / qte_poll_ms / qte_fast_ms / qte_sweep_ms /
    qte_sweep_relax_ms / qte_retry_ms / qte_retry_max / qte_stall_max / qte_model`
   (完整状态机与延迟预算见下文"QTE 闭环状态机""QTE 延迟预算"两节)。

## 坐标读取原理 (鼠标取点)

- 全屏地图下以鼠标为锚点, 按 `config.hover_box = [dx, dy, w, h]` (相对鼠标像素偏移,
  默认 `[0,-125,120,115]`, 2026-09-14 晚按实机裁图重新测量) 裁一小块屏幕 → 4× 放大 →
  **白字颜色掩膜** (近白+低饱和, 再按字符尺度过滤连通块: 明亮地形/绿色控制区不会糊掉白字) →
  Windows 内置 OCR → 正则 `[xy](\d{1,3}\.\d{1,2}|\d{4,5}|\d{1,3})` 配对, 取最后一组作为该点坐标。
  (交替必须**长模式在前**: OCR 偶尔丢小数点时 `x9613` 要还原成 96.13; 旧写法会先吃 3 位得到 9.61,
  `x10239` 更会错成 1.02 —— 距离直接差几百米。已加回归测试。)
  掩膜读不出且掩膜几乎为空时回退旧的全局阈值通道 (暗底场景)。
- 读数与游戏悬停标签完全一致; 鼠标不在地图内/标签被遮挡时返回空, 界面显示 `--`。
- OCR 字符纠错 `normalize_ocr`: `B→8 D→0 S→5 Z→2 O→0 l/I/|→1 ' , " →.` 等。
- 换分辨率/界面缩放后**无需改配置**: `hover_auto = true` (默认) 时按形状自动定位标签,
  见下一节; 置 `false` 才退回固定 `hover_box` + `FALLBACK_BOXES` 旧通道 (需按实机微调)。
- 配置框未命中时自动重试放大框 `FALLBACK_BOXES = ((-90,-170,280,240), (-160,-60,320,260))`,
  容忍标签相对鼠标的偏移差异 (窄框切掉 x/y 轴字符是此前"读不到坐标"的主因)。
- 后台轮询每 0.6 s 读一次鼠标旁标签并缓存; 光标停在 HUD 上时不写缓存/不提交跟踪,
  防止把 HUD 自己显示的数字读回去 (主窗在游戏中被盖住, 屏幕上始终是游戏画面, 无需避让)。
  F1/F2 实时读失败且缓存 <2 s 时采用缓存 (日志标注 `悬停缓存`)。
- 实时跟踪 (`config.live_target`, F8): 轮询读到新坐标即提交为目标并刷新 HUD;
  关闭后目标冻结为最后一次读数, 炮位始终只由 F2 更新。
- 排查: exe 同目录 `artillery.log` 记录每次按键的读取结果/来源、后台轮询异常、刷新异常;
  超 1 MB 自动轮转为 `artillery.log.1`; 界面日志框只保留最近 2000 行。
  读取失败时 `debug_hover/` 保存三次裁图 (crop0/1/2.png) 与 OCR 原文 (crop*.txt), 据此可精确调整 `hover_box`。

### 分辨率自适应 (2026-09-20)

`config.hover_auto = true` (默认) 时, 标签定位与取值都不再绑定本机分辨率/缩放:

**定位** `_auto_label_regions(img, mx, my)`
- 搜索区 `AUTO_SEARCH_BOX = (-340,-380,680,660)`: 以鼠标为中心的大窗口, 覆盖标签在
  不同分辨率/界面缩放下相对鼠标的各种偏移 (旧版固定 `hover_box` 换分辨率就切歪)。
- 白字掩膜 → 连通块 → 按块宽高比/密度/与鼠标距离打分, 输出两类候选:
  **块候选** (整个两行标签) 与 **行候选** (单行 `xNN.NN`), 各按距离排序。
- 两级亮度门槛 `DETECT_FLOORS = (170, 130)`: 一级 (170) 零候选才降到二级 (130),
  明亮地形/雪地不误检, 暗底场景不漏检。
- 距离门槛按字高自适应: `dmax = min(dmax, max(55, 7.0*hmed))`。实测真标签
  d/hmed = 4.6~6.5, 最近的干扰候选 ≥7.6 → 取 7 倍, 两侧各留约 8% 余量:
  既不会把旁边的地形亮点当标签, 也不会在大字号下把真标签筛掉。

**识别** 掩膜配方族
- 常规族 `ROBUST_RECIPES`: 先放大再二值化 (高分屏的正常路径)。
- 低分辨率族 `ROBUST_RECIPES_M1`: **先按 1x 原图取颜色掩膜 → 再放大掩膜 → 二值化**,
  小字放大后笔画糊成一团时仍能保住字形 (1080p 档的关键)。字高中位数 <9.5 px 时优先跑。
- 早退条件是"双轴齐" (`group_xy`); 只读到单轴不返回, 继续跑下一个候选凑另一轴。

**取值四级回退** (前一级拿到就返回)
1. 严格正则 + 常规 OCR: `([xXyY])(\d{1,3}\.\d{2}|\d{1,3}\.\d(?!\d))`
   —— 2 位小数优先; 1 位小数仅当其后无数字 (防 `y102.39171.28` 连读把 y 毙掉,
   又防 `x71.2` 这种截断读混进第一级)。
2. 严格 + 低分辨率鲁棒重采 / 单行重读。
3. 跨候选凑轴: 块候选给 `y102.39`、行候选给 `x71.28` 时拼成一对
   (同一时刻全屏地图只有一个悬停标签, 跨候选配对不会张冠李戴)。
4. 宽松 `extract_pairs_loose`: OCR 数字全对但丢了小数点 (`x7128` → 71.28);
   只认"字母紧跟 4~5 位数字", 拒绝低分辨率残读 (`x/ 1 28` 不会被猜成 1.28)。

**预算**: 每次读取最多 `MAX_OCR_CALLS = 14` 次 OCR 调用, 且每跑完一个候选立刻尝试
凑双轴早退; 配额用尽后仍会把已有结果再凑一次。本机档单次读取 0.04~0.06 s,
1080p 档 0.085 s, 后台 0.6 s 轮询完全跟得上。

**支持范围** (3600x1440 实机样张等比缩放实测, 真值 `x71.28 y102.39`)

| 相对本机屏宽 | 约合分辨率 | 标签字高 | 结果 |
| --- | --- | --- | --- |
| 1.75 ~ 0.58 | 6300x2520 ~ 2088x835 | 26 ~ 9 px | 全部读对, 单次 0.06~0.6 s |
| 0.5333 | **1920x1080** | 8 px | 读对, 单次 0.085 s |
| < 0.52 | 1600x900 / 1366x768 | ≤7 px | 不稳定 (系统 OCR 极限), 见"已知限制" |

误报对照 0/60: 鼠标停在空旷地形/地形亮点上时全部返回空, 不会凭残字编坐标。

## 射距解算

- 1 地图单位 = 100 m; 距离 = `hypot(dx, dy) * 100`; 方位 = `atan2(dx, dy)` (0°=北, 顺时针)。
- 仰角 mil 查 `range_tables.json`: 社区完整射表 (wardogshub.gg, 2026-09-10)
  L81 单弹道 84 点 (80~697 m), SPH-2 低弧 59 点 / 高弧 79 点; 分段线性插值。
- **L81 迫击炮射程窗口 132~684 m** (最远 684 m 游戏内实测): 超远/过近时读数转红 +
  HUD 追加 ⚠超远/⚠过近, 由玩家自行决定是否换炮。
- 射表标定: 主界面 [标定] 行, 射击场实测 (距离, 瞄具密位) → [记录] 写入 `table`,
  在 ±1 m 内覆盖社区点并叠加修正; [取距离] 自动填入当前解算距离。
- **距离标定 (2026-09-15)**: 真实距离 = 地图距离 × `distance_scale` + `distance_offset_m`,
  按武器存在 `range_tables.json` 的 `calibration` 里 (SPH-2 当前 **+70 m**, L81 无修正)。
  射程窗口判定、密位插值、HUD 全部使用标定后距离, 读数旁给出
  `距离修正 1102→1172m` 之类的提示; 主界面 [标定] 行第二行 [距离修正] 框直接改, 回车/失焦存盘。
  只有一个标定点时无法区分 "常数偏移" 与 "比例误差": 拿到第二个不同距离的实测点后,
  可改用 `distance_scale` (例如 1.0635) 复核, 两者代码都已支持。
- 高差修正: 射表为平地实测, 目标高于炮位时经验上按高差补 mil。

## 射表来源与核验 (2026-09-15)

- 游戏里的 "PZH" 即本项目的 **SPH-2** (PzH 2000 原型); hub 车辆表与游戏 pak 中都没有 "PZH" 这个名字。
- 公开射表 (wardogshub.gg 计算器、GitHub `apollyon-sys/wardogs-calculator`) 2026-09-15 复查仍是
  **alpha-1 社区实测表**, 与内嵌表逐点一致; 官方 Season 1 更新说明 (9/9) 只改经济数值, 没有新射表。
- 社区表已知缺陷: 顶点处重复行 `[2629,610]` / `[2629,620]` (本项目保留 610);
  低弧 mil 20 附近有一个离群点 (物理模型反演在该点残差 −14.8 m)。
- 物理模型反演 (拟合参数 `work/fit_params.json`, 仿真/拟合脚本 `work/fit1.py`):
  hub 计算器内部用 `deg = (mil + offset) * dpm` + 空气阻力 `k*v^2` 的半隐式 Euler 仿真;
  对 139 个 SPH-2 实测点反演得 **rms 2.57 m** (高弧 rms 1.25 / max 3.4), 顶点 mil 612.86 → **2630.3 m**;
  模型端点 mil 0 → 1045.9 m、20 → 1166.2 m、1390 → 782.8 m、1400 → 738.4 m。
  同一模型拟合 L81 迫击炮 rms 8.1 m, 说明其社区表自洽性较差, 暂不改动。
- 地形高差 (dz) 尚未参与解算: bakurani 地形已下载并拼成 2049×2049 高度场
  (`work/terrain/bakurani_h.npy`, 1 地图单位 = 100 m = 12.5 个 8 m 采样, 行列方向已用卫星瓦片比对验证);
  抽样验证 "高弧忽略 dz 只差 +25 m (mil 1315.4→1321.1)", 低弧远程影响更大, 可作为后续地形感知解算。

## QTE 方向箭识别原理 (2026-09-22)

- 分割对象是箭头的**亮填充连通域** (灰度 180~248) 而不是暗描边: 填充域本身就是干净的
  实心箭形状; 暗描边域会被"当前选中箭"外圈高亮框的暗边并进去 (8-连通成一个组件),
  把 bbox 与形状全污染。
- 描边环检 = **合并带判据** (2026-09-22 重写): `band = ring1 | ring2`, 即紧贴填充域的
  第 1 圈 (箭自身的暗描边, 与背景无关) 和第 2 圈 (描边外层+背景) **合在一起统计**,
  要求 band 有效像素 ≥16、均值 <132、且灰度 <130 的暗像素占比 ≥0.45。两圈都亮才排除
  (天空/亮面小碎块)。
  **为什么放弃旧的"单圈双通道阈值"**: 用户实机截图 (3 支已按箭变绿 + 1 支白色待按箭) 里,
  目标箭的描边核心灰度是 **111~113**, 恰好高于旧 ring1 的 `<110` 暗像素判据 → 暗占比只有
  0.22, 整支箭被当作"两圈都亮"排除 —— 这正是"最后一个按不出来"的**检测层根因**。
  合并带 + 把明暗分界抬到 130 后: 目标箭 band 均值 104.8 / 暗占比 0.75 (0.67x~2x 缩放下
  仍 ≥0.50), 而桌面干扰块 146 / 0.23、光标块 173 / 0.00, 分离度充足。
  旧版还有一条 "ring2 亮衬底 ≥180" 判据, 实测 ring2 其实是**暗**的 (均值 90.2),
  方向写反、从未触发过, 已连同死常量一起删除。
- 方向判定: 填充域 resize 到 32x32 后与运行时生成的 4 个标准箭模板求 IoU, 取最大者,
  且要求 IoU ≥0.62、领先次大 ≥0.08 (真箭实测 0.83~0.94, 桌面干扰组件 ≤0.46)。
  **不能用质心判向**: 实心箭的三角头质量集中在基底, 质心反而偏向箭尾, 方向会整体判反。
- 同排聚类 (中心 y/高度/水平间距) 后取 ≥2 箭的最大簇, 按 x 排序输出, 即按键顺序。
  聚类另加**行规整度**: 第 2 支起间距须在首间距 0.6~1.5 倍内、每箭长边 max(w,h) 须在
  首箭 0.85~1.18 倍内 (真 QTE 行间距近似等差、箭等大; 桌面/游戏 UI 偶然凑对的亮块
  间距随机, 在此被滤掉, 降误报)。
- 无模板文件、无固定像素尺寸 → 与悬停标签同一套分辨率自适应思路。
- 轮询区域 **两级** (v1.2): 未锁定箭行 = 主显示器中央横带 (虚拟屏全带含副屏太宽, 浪费 CPU);
  一旦识别到箭行, 改用 `qte_track_region()` 由**选中行** bbox 推出的紧凑小窗 (左 4 / 右 14 /
  上下各 3 倍箭高; 右侧那 14 倍是留给"逐支往右弹出"的后续箭, 实测 ≈8.5 支箭距 —— 这条余量
  就是"最后一支按不出来"不会因提速复发的保险), 每 `qte_sweep_ms` 仍全横带扫一次兜底
  (本行已按过键且画面正常推进时放宽到 `qte_sweep_relax_ms`, v1.3)。

## QTE 闭环状态机 (2026-09-22)

**WARDOGS 实测行模型 = 消耗型**: 按对的箭立刻变绿, 变绿后检测器就看不到它了
(实锤: 用户截图里 3 支已按箭是绿的、只有第 4 支是白色待按箭, 检测器只报出 1 支)。
所以"检测到的行"就是"还没按的尾段", 状态机以**画面为准**推进, 不以"我按了几次"为准:

| 画面 | 动作 |
|---|---|
| 与上一帧相同且该帧已按过 | 沉默, 等游戏把箭吃掉 (提前连发 = 与游戏失步 = 行尾永久卡死) |
| == 记录行尾段 `R[off:]`, off = 已按数 | 正常推进, 按下一支 (`off-1` 兼容最左箭淡出残影) |
| 跳得比已按数更前 (漏帧) | 以画面重新对齐后再按, **不重按整行** |
| 落后于已按数 (我们多按了) | 沉默等画面追上, 不重置 |
| 以 `R` 为前缀且更长 | 行还在向右弹出, 只更新记录, 不提前按 |
| 整行按完 / 已按区的淡出残行 | 沉默, 无保险重发 |
| 只剩 1 支孤箭且不是期望尾段也不是残行 | 忽略, 但**不清状态** (行中噪声); 空状态时孤箭不开新行 |
| 连续 4 帧空 | 认定箭行消失并复位 (单帧截屏撕裂不清状态) |
| 与记录行对不上的新行 | 2 帧防抖后从第一支开始 |

- **每键延迟** (v1.3): 按下后进入 `qte_fast_ms` (默认 2 ms) 快速重轮询, 越早看到“游戏吃掉了
  那支箭”下一键就越早发出。锁定紧凑小窗后单轮只要“抓图 6.9 ms 地板 + 识别 ~2 ms ≈ 9~12 ms”,
  端到端实测 **本工具每键开销 ≈165 ms (v1.1) → ≈45 ms (v1.2) → ≈18 ms (v1.3)**,
  键间隔地板 = 游戏自身消耗延迟 + ~18 ms, 详见下文“QTE 延迟预算”。
- **丢键兜底 `qte_retry_ms`** (默认 900): 画面持续不变且已按过时本应沉默, 但按键可能丢失
  (游戏以管理员运行时 UIPI 会拦掉普通权限进程发的键、中途切窗、按键被别的程序吞掉),
  那时一味沉默会把整行白等到 QTE 超时。超过 `qte_retry_ms` 就**补发画面最左那支一次**,
  且**不推进记账**, 画面追上后仍走正常对齐路径, 不会多发也不会漏发。
  900 ms >> 实测最大显示滞后 (~230 ms = 3 个轮询周期), 因此不会退化成旧的"提前连发失步"。
  设为 `0` 可关闭 (关闭后丢键就整行卡住, 见回归用例 C16)。
  补发取 `dirs[0]` 而不是 `R[已按数]`: 键丢失时游戏仍停在原位, 用记账下标会多跳一支按错键。
- **补发次数上限 `qte_retry_max`** (默认 3): 真实丢键补发 1 次就够, 上限是防止画面长期
  不变时 (QTE 失败后残影 / 暂停帧 / 关闸联调静态样张) 每 `qte_retry_ms` 无限补发狂敲方向键。
  额度在**画面变化**或**箭行复位**时自动恢复, 所以正常一行内多次丢键仍能逐个救回
  (回归 C15: 连丢 2 键 -> 补发 2 次 -> 整行 4 键零误按; C18/C19: 全部丢键 -> 恰好补发上限次)。
- **卡死看门狗 `qte_stall_ms` / `qte_stall_max`** (默认 2500 / 2): 补发额度用尽画面仍不变
  (连续丢键的长突发), 旧逻辑会从此永久沉默到 QTE 超时 (= "卡在一半不输入" 的第二条
  路径)。冷却 `qte_stall_ms` 后强制重决策一次: 先按画面回纠记账 (真消耗数 = 行长 -
  剩余白箭数), 下一轮走变化分支按画面最左支; 每行至多 `qte_stall_max` 次, 暂停帧/
  静态样张不会被无限重敲。`qte_stall_max=0` 恢复旧的硬上限 (回归 D8)。
- **重复行不再卡一半**: 消耗型下 "剩余白箭 == 已按前缀" (如 右,上,右,上 按到 2/4) 是
  合法中间态; 旧代码把仅适用于静止型的 `dirs == P` 判断用在了消耗型上, 在这里永久
  沉默 = 用户报 "极低概率卡在一半不输入" 的主路径。现在消耗型跳过该判断继续尾段
  对齐 (回归 `work\sim_qte4.py` D1~D6; A/B 对照: 旧逻辑在该行必卡 ci=2)。
- **`qte_model`** (默认 `consume`): 设 `static` 切回旧的静止型语义 (箭按完不消失的游戏:
  没有画面反馈也靠"行向右增长"继续往右按), 此时"画面不变即沉默"与丢键兜底自动失效。
- F10 手动单次仍走开环 `_qte_send` 整行连发, 不受状态机影响。
- 回归覆盖 (全部通过): `work\sim_qte2.py` 静止型 14 例、`work\sim_qte3.py` 消耗型 20 例
  (含显示滞后 0~4 帧、淡出残影、单帧撕裂、行中孤箭噪声、首键/中途丢键恢复、
  兜底关闭对照)、`work\sim_qte4.py` 重复行/看门狗 10 例 (含与旧逻辑的 A/B 对照)、
  `work\live_loop_real.py` **真实像素**闭环 lag=0~3 各恰好 4 键零误按、
  `work\test_qte2.py` 检测器正负样本 (含 0.67x~1.0x 缩放)、
  `work\probe_clip_qte.py` 全部历史截图/剪贴板样张识别结果与 v1.1 **逐项一致** (提速零回归)、
  `work\test_qte_band.py` 两级截屏区 9 例、`work\test_qte_speed.py` 端到端提速 5 档。

## QTE 延迟预算 (1440p 实测)

### v1.3 (2026-09-25, 延迟收尾: 轮询 / 兜底全扫 / 定时器)

| 措施 | 内容 | 实测收益 (端到端仿真, `work\test_qte_speed.py`) |
|---|---|---|
| `qte_poll_ms` 80→50 | 箭行刚出现 → 首键 的等待减半 | **首键 137→107 ms (-30 ms)** |
| `qte_fast_ms` 5→2 | 按键后 0.45 s 快速窗的 sleep 缩短 | 每键 -2~4 ms |
| `qte_sweep_relax_ms`=900 (新键) | 已锁小窗且本行已按过键时, 250 ms 一次的全横带兜底放宽到 900 ms; 行消失/抓空/未按键自动回 250 | 去掉跟踪期每 250 ms 一次 ~42 ms 离群帧 |
| 启动 `timeBeginPeriod(1)` | 全进程定时器 1 ms 格, atexit 还原 | 本机无差; 干净机器省 ~10 ms 级 |

不同游戏消耗延迟下 v1.2 → v1.3:

| 游戏消耗延迟 | v1.2 总耗时 | v1.3 总耗时 | v1.3 首键 | v1.3 键间隔 |
|---|---|---|---|---|
| 100 ms | 0.605 s | 0.589 s | 107 ms | 123 ms |
| 140 ms | 0.796 s | 0.742 s | 106 ms | 159 ms |
| 180 ms | 0.950 s | 0.911 s | 107 ms | 203 ms |
| **220 ms** (校准点) | 1.081 s | **1.062 s** | 107 ms | **238 ms** |
| 260 ms | 1.256 s | 1.216 s | 107 ms | 278 ms |

> **为什么不再快了**: 220 ms 档键间隔 238 ms = **游戏消耗 220 ms (93%) + 本工具 ~18 ms (7%)**
> (小窗抓图 6.9 ms 一帧地板 + 识别 ~2 ms + 一轮 sleep 2~5 ms)。
>
> **剩余空间上限**: 就算抓图完全免费 (0 ms), 每键开销也只能 18 → ~7 ms,
> 一行 4 键省 ~30 ms, 相对 1.06 s 总耗时 **< 5%**, 且实测拿不到 (见下)。
>
> **两条 GPU 取帧路径实测排除**:
>
> | 路径 | 内容正确性 | 延迟 | 结论 |
> |---|---|---|---|
> | dxcam (DXGI DDA) | 本机 HDR 下表面是 `rgba16f` FP16, 按 BGRA8 解读 → 花屏 (**格式错配, 非驱动 bug**, 修正早前判断); 正确解码后 `cv2.cvtColor` 不支持 float16 | `acquire_frame` 30 帧 715 ms ≈ **24 ms/帧**, 不比 GDI 快 | 弃用 |
> | windows-capture (WGC) 2.0.1 | 与 mss **逐像素一致 (max diff = 0)**, `find_qte_arrows` 结果相同; 36 次画面切换 8 s 内帧龄 1~20 ms 保持同步 | 配对实测 mss 中位 **17.3 ms** vs WGC 中位 **20.3 ms**; 配对差 (mss−wgc) mean −5.4 / median −9.1 ms → **WGC 更慢** | 弃用 |
>
> WGC 慢的原因: 帧要经 DWM 合成再投递给捕获管线, 这条链路的时延不低于 GDI 直接读屏幕,
> 所以“变更检测”不会更快 (探针 `work\probe_wgc12.py`, 同进程 / 同 250 ms 翻转源 / 双路径并行)。
> dxcam 探针: `work\probe_wgc.py` (DDA 表面格式 + 帧耗时)、`work\probe_dx_final.py`、
> `probe_dx_dump.py`; WGC 内容一致性: `work\probe_wgc3.py` / `probe_wgc8.py` /
> `probe_wgc10.py` / `probe_wgc11.py`。
>
> WGC API 踩坑备忘: `WindowsCapture(cursor_capture=False, draw_border=None, monitor_index=1)`
> —— `monitor_index` 是 **1-based**; **Win10 上 `draw_border=False` 会抛异常, 必须传 `None`**;
> 回调里 `frame.frame_buffer` 是零拷贝视图, 必须 `np.ascontiguousarray` 复制后再用。
>
> **结论**: v1.3 已贴物理地板, 瓶颈在游戏自身消耗延迟。`qte_poll_ms` / `qte_fast_ms` /
> `qte_hold_ms` 也都已在下限附近, 再降只多耗 CPU 没有收益。想再快只能等游戏变快。

`qte_poll_ms` 只影响“箭行刚出现”到“按下第一键”的等待 (锁定小窗后走 `qte_fast_ms`),
调小更跟手但空闲 CPU 占用线性上升, 弱机器可调大; `qte_sweep_ms` 调大少几次全扫 (更省 CPU),

### v1.6 红箭彩色通道的边际成本 (2026-09-26, 静态样张决定性 A/B)

> **量法** (数字诚实的前提, 踩了两个坑才定下来):
> ① **活屏做 A/B 不可比** —— `find_qte_arrows` 只在"灰度通道抓空"时才跑红分支, 而游戏画面在动,
> 灰度有时抓得到候选就把红分支整条跳过, 差值随之乱跳 (同一块全横带区域, 一次测出 +21 ms
> 一次测出 +1.25 ms)。改成**固定样张**连跑 K 次, 内容完全一致, 差值才是红通道净成本。
> ② **`process_time` 在 Windows 上的记账粒度 = 系统时钟节拍** (本机 15.625 ms;
> `timeBeginPeriod(1)` 改的是 sleep 唤醒粒度, **改不了 `GetProcessTimes` 的线程时间记账**),
> 所以单次/小批量测亚毫秒项必然量化成 0。必须"**批量 K 次测总量再除 K**", 让每个数据点累积
> 20~40 个量子 (相对误差 ≤3%)。
> 脚本 `work\probe_cpu_v16e.py` (静态样张) / `probe_cpu_v16d.py` (区域尺寸扫描)。
> 全程 **不动鼠标 / 不抢前台 / 不发任何按键** (发键与写盘的方法全 stub 掉), 进程降 BELOW_NORMAL,
> 因此可与用户实战同屏跑, 不干扰游戏。

| 样张 (内容固定) | 尺寸 | 红开 CPU | 红关 CPU | 净成本 | 存在闸 | 命中通道 |
| --- | --- | --- | --- | --- | --- | --- |
| 红箭真样张 (灰度全瞎) | 0.73 MP | 46.9 ms | 22.4 ms | **+24.5 ms (+109%)** | 放行 | red |
| 负样本: 同图抹掉箭行 | 0.73 MP | 46.6 ms | 21.4 ms | +25.3 ms | 放行 | 无 |
| 负样本: 红棕集装箱 | 0.02 MP | 2.81 ms | 2.58 ms | +0.23 ms | **拦下** | 无 |
| 白箭 `qte_real2` | 0.35 MP | 20.6 ms | 18.8 ms | +1.8 ms | 拦下 | gray |
| 白箭 `qte_allwhite` | 0.25 MP | 15.2 ms | 17.0 ms | −1.8 ms | 拦下 | gray |

零件级 (红箭真样张 0.73 MP): `_red_present` 存在闸 **0.273 ms** / `_red_mask` 全帧掩膜
**0.781 ms** / `_qte_cands(红掩膜)` **20.6 ms** vs `_qte_cands(灰度掩膜)` 19.5 ms。
全横带 2.17 MP 零件: `grab` CPU 16.7 ms (墙钟 32.3 ms) / `cvtColor BGR2GRAY` 3.05 ms /
`_red_mask` 2.66 ms / `_red_present` 0.82 ms。

**怎么读这张表**:

- **白箭行零成本**: 灰度通道一旦抓到行, 红分支整条不跑 (+1.8 / −1.8 ms 属测量噪声)。
  这是最常见的情况 —— v1.6 对白箭玩法**不增加任何 CPU**。
- **净成本 = "多跑一遍候选检验"**: `_qte_cands` 红掩膜 20.6 ms ≈ 灰度掩膜 19.5 ms,
  所以红分支的代价基本就是"再来一遍连通域 + 逐候选环检/模板匹配", 与区域像素数成正比
  (0.02 MP +0.2 ms → 0.07 MP +0.05 ms → 0.73 MP +25 ms → 2.17 MP +47 ms)。
- **存在闸拦得住时几乎免费** (+0.23 ms): 画面没有饱和红, 一次 stride-4 抽样就返回。
- **真正付钱的是"画面里有红但没有箭行"**: 锈红集装箱/红色涂装这类偏红的画面会让闸放行,
  于是每次灰度抓空都要多付一整遍候选检验。本机冻结实况正是这种画面 (全横带 +47.5 ms)。
- **但这笔钱主要落在空闲兜底全扫上, 不在延迟关键期**: 学到紧凑窗后常规轮询只有 0.07 MP,
  红通道净成本 **+0.05 ms** —— 可忽略。全横带只作为 `qte_sweep_ms`(250) /
  `qte_idle_sweep_ms`(1000) 的兜底, 每 250~1000 ms 才一次。
- **调速器自动兜住**: 空闲态每轮 CPU 涨上去, `_qte_idle_delay()` 就把 sleep 抬到满足
  `qte_cpu_budget=25%` 为止 (`sleep >= cpu × (1/0.25 − 1) = cpu × 3`), 所以红通道在空闲态
  是**换成更低的扫描频率**, 不是换成更高的 CPU 占用。代价是"从未见过箭行、且画面偏红"时,
  首行发现延迟从 ~0.29 s 变到 ~0.47 s (全横带单轮 CPU 73 → 120 ms, 轮询率 3.4 → 2.1 Hz);
  一旦学到 `qte_zone`/紧凑窗就回到便宜路径, 这项差异消失。**延迟关键期不受调速器约束**
  (`tracking` 窗口内), 所以按键间隔不受影响。
- 绝对量级参照 (本节前面的真游戏同屏表): v1.5 默认姿态 **11.2% 单核 / 0.94% 全机**;
  QTE 空闲扫屏受 25% 预算封顶。v1.6 的 QTE 轮询实测 (绑定真实 `_qte_scan`,
  `work\probe_cpu_v16.py`): 空闲态 **34.8% 单核 / 2.90% 全机 / 占空比 22.0%** (未学条带,
  全横带兜底为主), 已学窄条带后 **21.8% / 占空比 13.1%** —— 均在 25% 预算内, 不会吃满一个核心。

- 高缩放屏 (125%/150%): 启动第一件事就把进程设为 **每显示器 DPI 感知**, 截屏/鼠标/窗口坐标
  统一为物理像素 (本机 125%: 3600x1440)。以前这一步是 mss 在后台线程里顺手做的, 会让坐标系
  在运行中从 2880x1152 突变成 3600x1440, 已保存的 `hud_pos` 随之错位; 现已固定在主线程启动时完成。
- 光标贴屏幕上/左边缘时悬停框会整块出屏, 此时返回空读数 (属正常降级, 不再抛异常)。

  标定 [记录]/[清空] 写表后立即失效重载。
- **分辨率下限**: 悬停标签字高 ≥8 px (约 1920x1080 全屏) 时读取稳定; 更低分辨率
  (1600x900 / 1366x768, 字高 ≤7 px) 已到 Windows 内置 OCR 的极限, 会读不到或偶发读错
  一位小数。缓解: 游戏内把分辨率或界面缩放调高, 或改用 ≥1080p。
  若某台机器界面布局特殊导致形状搜索失准, 可置 `config.hover_auto = false`
  退回"配置框 + `FALLBACK_BOXES`"旧通道并手工微调 `hover_box`;
  读取失败时 `debug_hover/` 的三次裁图 + OCR 原文可精确定位问题。
- **QTE 分辨率下限**: 方向箭填充域边长 ≥15 px (样张缩放到 ≈0.53 倍, 约等同 900p 全屏)
  时整行识别; 再小 (0.45 倍, ≈720p) **带白色选中框的那支箭**可能因框线抗锯齿并入填充而
  形状畸变被漏掉 (其余箭仍正确, 不会编造方向) —— 表现为少按一个键。缓解: 游戏内分辨率/
  UI 缩放调高。无选中框的箭行在 0.45 倍下仍整行可识别。
- QTE 识别只认"暗描边+亮填充"的方向箭 glyph; 若游戏更新改了箭头配色/形状, 需重测阈值。
  当前阈值按用户实机截图校准 (目标箭描边核心灰度 111~113, 合并带均值 104.8 / 暗占比 0.75)。

  (独占全屏/被完全遮挡) 就无法推进; 前台闸开启时切出游戏会立即停止识别与按键。

## v1.6.5 (2026-09-26) — 抗画面变化的自适应亮度通道（识别鲁棒性）

### 用户报告与结论

> "现在很多输入错误，是识别问题还是输入问题？错误率必须控制到最低。"
> "画面变化导致这个箭头可能会出现一点色差或者其他之类的吗？图像识别的鲁棒性一定要强。"

**结论：v1.6.4 把输入侧收口之后，剩下的失手主要是识别问题，而且病灶非常具体——主通道的"绝对亮度窗"。**

`find_qte_arrows` 主通道用 `QTE_FILL_GRAY = (180, 248)` 这个**绝对**灰度窗分割箭填充，再用暗描边环检排掉天空。
绝对窗的隐含前提是"画面亮度大致恒定"，而 WARDOGS 的战场恰恰不恒定：炮口火光、爆炸闪光、夜战、烟雾、
泛光(bloom)、暗角、大面积逆光……只要整幅画面被抬亮/压暗 25 个灰阶以上，箭填充就整体滑出 180~248，
**一整行箭直接抓空**（EMPTY）——闭环无键可按，表现出来就是"没反应"或"少按一支、整行重来"。

全量扰动实测（`work\robust_ab.py`，8 张真样张/合成样张 × 81 种扰动 = 648 次）：

| 扰动档 | 主通道精确命中 | 现象 |
| --- | --- | --- |
| `bright +40` / `bright -60` | 1/8、1/8 | 整幅抬亮 / 压暗 |
| `flash 0.2 ~ 0.35` | 1/8 | 爆炸闪光 |
| `night 0.45` | 0/8 | 夜战暗幕 |
| `veil- 0.3 / 0.45` | 1/8、0/8 | 烟雾 / 半透明暗幕 |
| `bloom 3 / 6 / 10` | 1/8 | 泛光（三档全丢） |
| `haze 0.5` | 3/8 | 雾 |
| **合计（648 次）** | **78.1%** | 失配形态 `EMPTY 123 / COUNT 19 / WRONGDIR 0` |

关键是最后那个 `WRONGDIR 0`：**失手几乎全是"整行抓空"，不是"方向认错"**。
这也解释了为什么 v1.6.4 的状态机再怎么加护栏都收不到底——护栏防的是"读花"，防不了"读空"。
反过来，方向判定本身与亮度无关（IoU 跑在二值掩膜上），色相/饱和/色温/JPEG/噪声/缩放六族本来就 100% 通过。
所以要修的不是"认方向"，而是"哪些像素算填充"。

### 修法：只在抓空时才付费的四条"相对分割"备援通道

主通道（灰度 + 红箭彩色）都抓空时，才启用 `_qte_adapt_cands`，四条相互独立的**相对**分割法依次上场：

| 方法 | 做法 | 治什么 |
| --- | --- | --- |
| `th25` | 顶帽 `gray - blur(gray, 25)` 再 Otsu | **主力**。对整体亮度偏移**数学上完全不变**：`(g+v) - (blur(g)+v) = g - blur(g)`；对泛光/暗幕/gamma 近似不变 |
| `th61` | 同上，核 61 | 大箭 / 模糊、泛光下补全整行 |
| `otsu` | 全局 Otsu 取亮侧 | 阈值随直方图走，治均匀变亮/变暗 |
| `clahe` | 局部对比度均衡后仍用原窗 | 大面积逆光 / 局部强光 |

四条都还要再过**全套门**：掩膜密度闸、连通域数闸、尺寸门、填充率、**相对**描边环检（`QTE_REL_*`，
与填充自身亮度比而非绝对灰度）、更严的形状门（IoU 0.66 / margin 0.10，主通道 0.62 / 0.08）、行规整度。
所以最坏情况是"仍然抓空 = 等下一轮"，**不会退化成"按错键"**——沿用 v1.6 以来的 fail-safe 取向。

三道"分割退化"闸（实测标定，`work\shaft_probe.py`）：相对分割在"整幅都是纹理"的画面上会把大片背景当填充
（亮底细十字 38.8%、白面板 62.3%、天空噪声 23.7%、栅栏 56.9%），而真 QTE 箭行只有 2.9%~12.8%。
这种分割已经不是"找箭"而是"找亮块"，直接在掩膜层判废（`QTE_ADAPT_MAX_DENSITY 0.18` / `_GLOB 0.45`、
`QTE_ADAPT_MAX_COMP 1200`）——既堵掉唯一一类能凑成 ≥2 箭的误报，又省掉后面连通域那笔钱
（天空噪声图 13917 个域 ≈ 28 ms 白烧）。

### 多法之间怎么挑：最左 x 优先（首键保护）

原来写的是"首个够用就返回"，实测发现两个坑（`work\adapt_bestfit.py` / `adapt_guard.py` / `adapt_xguard.py`，180 次）：

* 首个够用会让 `th25` 的**半行**截胡 `th61` 的**整行**（泛光/暗幕/模糊下 th61 常能补全）；
* 但一味取"箭数最多"又会把首键正确率拖下去（95.6% → 95.0%）。

闭环里真正致命的不是少读一支箭（状态机的增长确认/消耗佐证能自愈），而是**最左那支丢了**：
工具会把第二支当成待按的第一支发出去，游戏判错，整行重来。实测所有首键失手都是"结果 = 真值的后缀"，
没有一例方向判错（`work\bloom_probe.py`）。所以出货选法是：

1. 先用"行头 x 最小"锁定行头——谁的行头更靠左，谁更可能没丢箭；
2. 只保留行头与它相差 ≤ `QTE_ADAPT_XTOL(0.6)` × 箭宽的集合；
3. 在其中取"箭数最多 → 中位置信最高"；
4. `QTE_ADAPT_GOOD(4)` 早退：某法已给满 4 支就不再试后面的法（本作行长绝大多数为 4；
   与"四法全试"结果逐位相同，却省掉约一半分割开销）。

## v1.6.6 (2026-09-26) — 红色箭行 = 失败反馈，不是可按提示（输入错误率收口）

### 用户报告与结论

> "红色是错误输入哦，你应该没有搞错吧？"

**没搞错方向，但搞错了语义 —— 而且这个语义错正是用户报的输入错误的大头。**

`find_qte_arrows` 里从 v1.6 起就有一条"红箭彩色通道"：灰度通道抓空时，用 HSV 红掩膜再找一遍箭，
找到就以 `src="red"` 出货、**直接进按键管线**。当时的假设是"游戏可能用红色高亮当前该按的那支箭"。

实际语义恰好相反：WARDOGS 里**整行箭变红是"上一行按错了"的失败反馈**，那一行已经判死、不会再接受输入。
于是形成一条自我强化的错误链：

```
按错一键 → 整行变红 → 工具把红行当成新提示继续发键 → 又"错" → 整行重来
```

v1.6.5 的 648 次 A/B 里 `src=red` **接管了 73 次**，也就是 73 次向已经判死的行发键。
用户截图里"整行红"正是这么来的。

### 修法（一）识别层：三道否决闸，红像素永不做可按键候选

`artillery_tool.find_qte_arrows` 新增 `red_press=False` 形参（默认关；只有 A/B 复现旧语义时才传 `True`）。
默认路径下红色像素**一律不产生可按键候选**，改为触发整帧否决：

| 闸 | 判据 | 常量 |
| --- | --- | --- |
| 红存在闸 | 每帧先廉价地数一遍"有没有足够多的饱和红像素"，无红立即放行（白帧只花 ~0.12 ms） | — |
| 形状闸 | 检出 **≥2 支红箭形状** → 整帧否决 | `QTE_RED_VETO_MIN = 2` |
| 孤红 + 灰空 | 只有红、灰度通道空 → 否决（堵住"红痕残留但箭已消失"的半帧） | — |
| 中心饱和闸 | 候选行中心的饱和度超阈即判红 | `QTE_RED_SAT = 45` |

否决帧把 `stats` 写死成 `src=None`、`red_row=True`、`margin=1.0`，`red_n` 照常给出（GUI 限流要用它续快轮询窗）。
源码级不变量（测试 H 组逐条钉死）：**全工程只有一处 `src="red"` 赋值，且被 `red_press` 守住**；
`stats["src"]` 永不可能被写成 `"red"`；GUI 侧从不传 `red_press=True`。

### 修法（二）发键层：GUI 四道闸 + 250 ms 禁闭期

| 位置 | 行为 | trace 标记 |
| --- | --- | --- |
| `_qte_scan` | 认出红行 → `_qte_red_veto(kind)` 后**立即 return**：不学窗、不喂状态机 | `red-fail-ignore` / `red-idle-ignore` |
| `_qte_maybe_send` | 禁闭期内一律不按（每帧记账） | `red-hold` |
| `_qte_press_gated` | 按键门在禁闭期内直接返回 `False` | `gate-redhold` |
| `_qte_send_one` | 发送线程里**已在途**的键也丢弃（否决发生在一键飞出去的途中也拦得住） | `drop-redhold` |

* **禁闭期 `qte_red_hold_ms = 250`**：失败动画会留白残影/半帧，250 ms 内连**白行**也先不按，
  等动画过去再重新走首键防抖（`qte_press_stable_ms = 60`）。设 `0` 则只停当前帧。
* **死行记账**：闭环里若已有记账行，记成死行清空（`row=[] pressed=[]`），不留半截状态污染下一行。
* **提示去重 `_qte_red_logged`**：一次失败只在界面提示一次，真发键后复位；
  空闲否决走 `red-idle-ignore` 完全不刷日志（实测红行持续 0.6 s、112 帧只出 1 条用户日志）。

### 病灶一：前台闸一帧就停摆（卡几秒）

`_game_foreground()` 原本是"这一帧前台不是游戏进程就立刻停扫描"。实际机器上前台会有各种瞬时
抖动（置顶 HUD、覆盖层、游戏自身窗口事件），闸门跟着翻，闭环每翻一次就断 0.5~2 s。

而且 HUD 是 `overrideredirect + topmost` 的置顶窗，只加了 `WS_EX_TRANSPARENT | WS_EX_LAYERED`，
**没有 `WS_EX_NOACTIVATE`** —— 置顶窗一旦被系统给了激活，游戏就收不到方向键（表现就是"按了没反应"）。

**修法**：

| 项 | 做法 |
| --- | --- |
| 迟滞 | "不是游戏"必须**连续保持 `FG_FLAP_MS = 400`** 才真的停摆；瞬时抖动直接忽略 |
| 行内宽限 | 本行已经开始（按过键 / 1 s 内见过箭行）时**一律不许中途关闸**，整行一口气打完 |
| 诊断 | 闸门真要关时，日志报出**是谁抢了前台**（`前台不是游戏 (前台=xxx.exe): …`），下次一眼定位 |
| 不抢前台 | HUD 窗口样式补 `WS_EX_NOACTIVATE (0x08000000)`：置顶可以，**永远不许抢激活** |
| 发键安全 | 发键前那道**严格**前台检查原样保留（`_qte_send_one` 直接问 `_game_foreground()`），<br>迟滞版只给**扫描**用 —— 挡"切去 QQ/浏览器乱发方向键"这条红线不动 |

### 病灶二：亮天空被"孤红闸"误杀（v1.6.6 引入的回归，我认）

亮天空上箭填充和背景几乎同亮度（实测天空灰度 204、箭填充 204~206），箭是靠**暗描边**分出来的；
主通道的描边环检用的是**绝对**暗门（`<110` / `mean<130`），实机天空描边是 97~162 的中灰 ——
三道绝对环检全灭，主通道**必然抓空**，只能等 400 ms 一次的自适应通道。

而 v1.6.6 的否决顺序是：

```python
cands = 灰度通道候选
veto  = (red_n >= 2) or (red_n >= 1 and len(cands) < min_arrows)   # <-- 这里就 return
... 自适应通道 (根本没机会跑)
```

也就是说：**灰度通道抓空 + 画面上有 1 支凑成箭形的暖色/红色痕迹 = 整帧被判成"输入失败反馈"**，
自适应通道还没跑就被否掉了。白天空 + 暖阳/夕阳/橙色集装箱正是这种画面。

**修法（两件一起）**：

1. **主通道在"亮底帧"也开相对描边环检**：新增 `_qte_bright_bg(mask)`，用 `QTE_FILL_GRAY`
   掩膜占比 `>= QTE_BRIGHT_BG_DENSITY (0.30)` 判定亮底；亮底帧把 `rel=True` 传给 `_qte_cands`，
   改用"描边比**填充自身**暗多少"这种与整体亮度无关的判据。白天天空不用再等自适应限流。
2. **否决顺序拆开**：
   * **形状闸**（`red_n >= QTE_RED_VETO_MIN = 2`）照旧最早退 —— 整行红箭一秒都别拖，自适应也不许兜底；
   * **孤红闸**（红 1 支 + 抓空）**挪到自适应通道之后**再判，而且要求**所有通道**都抓空才算死行。

## v1.6.9 (2026-09-26) — 点右上角 X 一次性结束父子进程

### 用户问题

> "帮我启动新版本，新版本能不能在点右上角退出时自己结束所有父子进程？"

**能。已实现并实测。**

### 为什么以前会留进程

PyInstaller `--onefile` 的形态是**父 bootloader + 子 app 两个进程**：

```
explorer/shell
   └── WARDOGS_Artillery.exe      ← 父: 解包 -> CreateProcess -> 等句柄 -> 拿退出码 -> 自己退出
          └── WARDOGS_Artillery.exe  ← 子: 真正的 tkinter 程序 + 后台线程 + keyboard 低层钩子
```

子进程一退，父进程**本来就会跟着消失**。所以关键是**子进程必须一定退得掉**。
而旧的 `on_close()` 只做：

```python
self._poll_on = False
core.shutdown_ocr()
keyboard.unhook_all()
self.root.destroy()
```

之后靠解释器自然收尾，有两类残留会拖住它：

* `keyboard` 库的**低层键盘钩子线程**在 `unhook_all()` 之后可能还在；
* 其它后台线程/子进程收尾期间又抛异常，异常被吞掉后进程就挂在那儿。

结果就是"窗口关了，进程还挂在任务管理器"——**单实例互斥锁一直被占着，新版根本起不来**。
这跟之前"版本号没变"其实是同一个坑的两面。

### 修法

```python
def on_close(self):
    self._poll_on = False                       # 停轮询
    self._qte_red_until = 1e18                  # 禁掉任何在途/排队的发键
    core.shutdown_ocr()
    keyboard.unhook_all()                       # 拆低层钩子
    self.root.destroy()
    _terminate_parent_bootloader()              # 显式收掉 bootloader 父进程
    os._exit(0)                                 # 兜底: 保证子进程一定退得掉
```

`os._exit(0)` 是关键的兜底：**不跑 atexit、不 join 后台线程、不等 GC**，本进程立刻结束；
父 bootloader 等待句柄返回后随即退出。再显式收一次父进程是为了杜绝任何残留。

**收父进程带严格安全闸**（这是最容易误伤的地方，必须写死）：

1. 只有 `sys.frozen`（真打包运行）才动手，源码 `python gui_app.py` 一律跳过；
2. 必须查到父进程的**映像路径 == `sys.executable`** 才 `TerminateProcess`。
   从 PowerShell / 终端 / 资源管理器里启动时，父进程是 `powershell.exe` / `explorer.exe`，
   路径不相等 → 直接跳过，**绝不会误杀 shell 或资源管理器**。

### 病根：一支杂散箭就能把真行藏起来

`_qte_scan` 原来是"**只要 `seq` 非空**就重学紧凑轮询窗 + 把兜底全扫往后推"：

```python
if seq:                                   # ← 1 支杂散箭也算

    self._qte_learn_zone(region, row, full)   #   还污染持久窄条带

```

而 `find_qte_arrows(min_arrows=1)` 会返回单支箭 —— 随后 `_qte_maybe_send` 把它当
`short-ignore` / `lone-ignore` 拒掉（拒得没错），**但窗已经学歪、全扫已经被推后了**。

## v1.6.11 (2026-09-28) — QTE 再提速: 消耗跃迁免稳定窗

### 用户问题

> "这个QTE速度还能再加快一点吗？"

### 每键时间都花在哪 (v1.6.10 实测)

`qte_trace.log` 里一次推进 = 看到消耗 (~15 ms) + **候选稳定窗 60 ms** (`qte_press_stable_ms`)
+ **最小键间隔地板 100 ms** (`qte_min_gap_ms`) → 落键间隔中位 ~123 ms。
稳定窗当初是为了挡"单帧读花": 同一候选要连续读到 60 ms 才按。

### 修法: 让"游戏吃掉键"这个事实自己当证据

消耗型行模型下, 按对一支后画面尾段会**正好缩掉最左那支**。于是:

```
上一帧读到 [h, b, c]  且 h == 刚按的那支
这一帧读到 [b, c]     == 上一帧[1:]        <- 逐位匹配, 就是消耗签名
=> 直接按 b, 免掉 60 ms 稳定窗
```

错读要**恰好**等于期望尾段才能骗过这道门 (方向、顺序、长度全对), 概率远低于稳定窗想挡的
瞬态读花; 真被骗也只是早按一支, 红行否决 / 补发 / 看门狗照旧兜底。五道前提缺一不可:
开关 `qte_consume_fast` (默认开) / 两帧间隔 <=0.4 s / 行进行中 / 上一帧首向 == 刚按的键 /
`dirs == prev[1:]`。红行禁闭、回前台 settle、margin 三道门**仍在快路径之前**。

同时 `qte_min_gap_ms` 基线 **100 -> 70** (仍远高于人类连打速度, 游戏按帧轮询输入,
70 ms = 4~10 帧间隔, 不会串键); 该键在 `MIGRATE_KEYS` 里, `CFG_VER` 166 -> 167,
旧配置首启自动拉回新基线。
